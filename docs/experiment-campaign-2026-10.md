# CLP transfer and comparative extraction campaign

Date: October 5, 2026. The user selected experiments 1-4 from the project review.
This work order makes the intended execution concrete; it records no new model
results and does not dispatch agents. The proposed primary owner is GPT-5.6
Sol / High. Use one continuing owner, with this file and CURRENT_WORK.md as the
resume points. Historical task numbers are references, not handoff boundaries.

## Working agreement

The owner implements, runs available jobs, repairs routine failures, imports
returns, analyzes evidence, prepares review, and validates the result. Finish
these activities within each milestone without asking the user to manage them.
Update CURRENT_WORK.md with verified outputs, exact pending dependencies and
the next executable action. Do not make the user reconstruct state from logs.

Use Astra/High selectively for a bounded scientific-protocol review and final
evidence audit, or a specific unresolved reasoning problem. These are recommended
reviews, not automatic agent dispatch or mandatory approval gates. Sol performs
routine self-review and fixes. A review request should contain the precise
question, relevant diff/artifacts and acceptance evidence, not the full history.
The coding agent's model is separate from models evaluated as extractors.

Deliver a reproducible comparison on existing development evidence before
requesting new annotation. Reuse the 200 CLP sections, T057/T062 development

new analysis or tuning on T067 is development evidence for future methods.

- Inspect and pin the actual sister-project V5.1 implementation and dependencies.
  Transfer its alternating-passage, inline/delimited list, table, recovery,
  orientation and acceptance behavior through a narrow boundary. Preserve the
  source structure it needs. The two-column `clp_table_v5_1` generator is a
  comparator, not an equivalent implementation of the complete CLP system.
- Replay saved CLP decisions only when inputs and configuration match. Distinguish
  replay from live execution. Include rules-only and full CLP variants and the
  existing S&H, Ab3P, PLOD pairing and Jev-judge comparators where applicable.
  Inventory existing results before rerunning them. If the full pipeline requires
  live requests beyond authorized access/budget, finish replay and independent work.
- Reconcile CLP's 143 positive, 50 negative and seven parser-extension sections;
  the exported count of 57 negatives combines different dispositions. Account for
  all 339 unmapped pairs. Preserve their exclusions explicitly; unmatched system
  output is not automatically false when reference coverage is incomplete.
- Report CLP-native normalized/string metrics and Abrex exact-offset metrics as
  distinct views with explicit denominators. Show mapping loss, section coverage,
  abstentions and article-group identities. No claim of independent validation
  follows from this development set.
- Break errors into candidate omission, source/structure mapping, endpoint

Acceptance: real comparable artifacts and an error readout, or a precise
host-dependent remainder with a ready bundle; focused tests plus the fast gate.
No new general framework or downstream entity experiment is part of this phase.

## Milestone B: source-grounded extraction versus candidate judging

Implement one direct extraction baseline and compare it with candidate judging
on the same development inputs. Reuse resolver, registry, job, caching and review
contracts. Direct extraction may propose pairs absent from existing candidates;
it must retain literal quotations and unambiguous occurrence locations, validate
Unicode offsets, and abstain or diagnose unsupported output. Do not repair output
using gold answers. Keep discontinuous evidence separate from exact pairs.

Prepare a concrete recommended model route, version, prompt, bounded pilot size,
request/retry/token limits and total monetary cap. Reuse already authorized
access; ask only for genuinely missing access or budget, after the runnable
adapter, fixtures and cost estimate are ready. Do not confuse the user's Codex
model choice with authorization for a new scientific-data API destination.
Keep any tuning on development material and record every tried configuration.

Acceptance: measured candidate coverage, final precision/recall, error types,
failure/abstention rates, latency and actual usage, with reproducible identities.
If human adjudication is necessary, deliver the minimal assisted queue described
below and continue work that does not depend on its answers.

## Milestone C: one frozen contemporary comparison

Build one concrete protocol after development findings, including native-offset
Ab3P, S&H, PLOD pairing, the complete CLP system, candidate judging and direct
extraction. Keep the requested experiments visible even if development finds a
method weak; any narrower confirmatory selection needs an explicit rationale.

Propose article-group sampling, source/structure strata, annotation workload,
matching policies, limits and success criteria together. Reuse settled semantics;
ask only for material new scientific decisions. Report prose and tables/lists
separately. Use a representative component for deployment questions and a
separately labeled structural challenge component; do not pool enriched samples
into a population estimate. Choose sample size from required uncertainty and
review burden, not a promise that another tiny sample will establish superiority.

Freeze methods, prompt/configuration, protocol and splits before confirmatory
execution. Exclude linked development articles and audit known CLP/dictionary
overlap. Preserve unknown training/resource overlap as a limitation. Obtain a
prediction-blind annotation lock before exposing evaluated predictions; run the
complete frozen comparison and report article-group uncertainty/concentration,
runtime failures and negative results. Never repeatedly resample until a win.

Acceptance: verified run/prediction/gold manifests, reconciled counts, per-stratum
and overall results, limitations and a concrete scientific recommendation. Run
the full quality gate at this campaign boundary. No automatic production adoption.

## Human work is a prepared decision, not clerical preparation

For development review, reconcile existing answers first using source identity,
exact occurrences and the applicable scope policy. Reuse valid decisions with
provenance; leave changed/ambiguous cases unresolved. Deduplicate proposals and
prefill spans, context, candidate relations and suggested dispositions with short
reasons. Keep agent proposals distinct from confirmed human annotations. Include
passage-search controls so an output-only queue cannot conceal common misses.
Never mark an unsearched passage complete or accept agreement as independent gold.

For blind review, preload source context, navigation, metadata and save/resume
controls, but no predicted answers. Reuse existing UI components. Verify the
actual packet and disposable persistence tests before delivery; do not create
fake human decisions in authoritative annotation files. Preserve prior work.

Every user handoff must state:

1. The remaining scientific question and number of passages/judgments, with a
   measured or explicitly estimated time burden.
2. A tested exact launch command or live link and the precise actions to take.
3. Where saving writes, how to resume, and the minimal return message, usually
   "review complete". The agent locates and validates the saved state itself.
4. What the owner will do next without another implementation assignment.

For server jobs follow the baseline runtime and Linux provisioning guides. Use
one self-contained bundle and copy/run/return instructions, expected success
output and an exact returned filename. Do not use historical WSL paths as server
defaults. When access is already available, execute/import directly; otherwise
leave only the unavoidable host operation to the user. Keep independent work moving.
